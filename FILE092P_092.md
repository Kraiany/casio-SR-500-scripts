# Casio SR-500 program file FILE092P.092 (AUTOPGM)

This document describes the binary file `AUTOPGM/FILE092P.092` of the Casio
SR-500 POS register: the register's program (settings) memory, which holds the
PLU (product) list with prices, department names, function keys, tax rates,
receipt message lines and more. The format is not documented by Casio. Everything
here was reverse-engineered from the file, and each statement is marked as
**confirmed** (checked against the data) or **probable / unknown**.

## Overview

| Property | Value |
|---|---|
| Location | `<export>/SR500_550_4000/AUTOPGM/FILE092P.092` |
| Size | 105,712 bytes (`0x19CF0`) |
| Copies | One per export under `data/`; all six are byte-identical (MD5 `f65a4db84d657d6a554e6aa7ceaee92b`) |
| Snapshot time | 2025-01-04 16:18 (stored in the file, matches the file date). Products added later are **not** in it |
| Text encoding | CP932 (Shift-JIS), padded with spaces |
| Structure | Text header, a 32-byte container header, then 24 tables, each preceded by a descriptor block, ending exactly at end of file |

It contains no sales data. Sales are in the EJ journals and the X/Z reports
(see [README_EJ_FORMAT.md](README_EJ_FORMAT.md) and the README). The files in
`BACKUP/` use the same container and block structure, but with compressed
records and report counters instead of settings; they are not covered here.

## Conventions

| Topic | Rule |
|---|---|
| Offsets | Hexadecimal, from the start of the file, unless stated |
| Integers | The format mixes byte orders (see below): `u16le` / `u32le` little endian, `u16be` big endian |
| BCD | Packed decimal, two digits per byte. Prices, PLU codes, tax rates, hours and staff numbers are BCD |
| `E` padding | In the PLU code, unused nibbles are filled with `E` (`0xE`), e.g. `1E EE EE EE EE EE EE` is code `1` |
| Text | CP932, space padded to the field width. Half-width katakana (single byte) occurs, e.g. `ｱﾙｺ-ﾙ` |
| Yen | Prices are whole yen with no decimals, 3 BCD bytes = 0..999,999 |

## File layout

```
0x0000  text header          "n:P0092:\r\n" 0x1A, then zeros                 (10 + 2 bytes)
0x007C  marker               "POn\0"
0x0080  container header     32 bytes
0x00A0  descriptor block (i) + table (f), repeated 24 times, to 0x19CF0
```

### Text header and marker

| Offset | Size | Content |
|---|---|---|
| `0x00` | 10 | ASCII `n:P0092:` + `0D 0A`. `P0092` is the file name (`FILE092P`, number 092) |
| `0x0A` | 1 | `1A` (DOS end-of-text mark) |
| `0x0B`..`0x7B` | | zeros |
| `0x7C` | 4 | ASCII `POn` + `00`. Meaning unknown (confirmed present) |

### Container header (`0x80`, 32 bytes)

| Offset | Size | Content |
|---|---|---|
| `+0x00` | 5 | Magic `68 2E 01 00 00` |
| `+0x05` | 5 | Time stamp, BCD `yy mm dd hh mm`, here `25 01 04 16 18` = 2025-01-04 16:18 |
| `+0x0A` | 6 | zeros |
| `+0x10` | 4 | ASCII `5178`. Meaning unknown (the same value is in the backup files examined) |
| `+0x14` | 12 | zeros |

The same 32-byte header starts every file in `BACKUP/` (there at offset 0).

### Descriptor block and table

After the container header the file is a sequence of pairs:

```
 i-block (descriptor)            f-block (table)
 +------------------+            +--------------------------+-----------------+
 | 69 00 | len | ... |  ------->  | 18-byte table header      | count x records |
 +------------------+            +--------------------------+-----------------+
```

The sequence continues until the last table ends exactly at the end of the file.

**Descriptor block** (`i`, `0x69`). Confirmed for all 24 blocks:

| Offset | Size | Content |
|---|---|---|
| `+0` | 2 | `69 00` tag |
| `+2` | 2 | `len` (`u16le`) |
| `+4` | `len - 1` | Payload. The table header follows directly after it, so `table = block + 4 + (len - 1)` |

Payload layout (confirmed that the field sizes always add up to the record size):

```
<table id: u16le> <A> <n> 00 <B> 00  <field 1> 00 <field 2> 00 ... <field n>
```

`n` is the number of fields, each field is `<code> <size>` (two bytes), and
fields are separated by a `00` byte. `A` and `B` are small numbers whose meaning
is unknown. Example, the PLU table (id 4), payload bytes:

```
04 00 09 07 00 02 00 22 07 00 0d 10 00 0e 04 00 10 02 00 0f 03 00 18 01 00 25 02
```

| Part | Bytes | Meaning |
|---|---|---|
| table id | `04 00` | 4 |
| `A`, `n`, `00`, `B`, `00` | `09 07 00 02 00` | 7 fields follow |
| field | `22 07` | code `0x22`, 7 bytes (PLU code) |
| field | `0d 10` | code `0x0d`, 16 bytes (name) |
| field | `0e 04` | code `0x0e`, 4 bytes (flags) |
| field | `10 02` | code `0x10`, 2 bytes (department) |
| field | `0f 03` | code `0x0f`, 3 bytes (price) |
| field | `18 01` | code `0x18`, 1 byte (zero) |
| field | `25 02` | code `0x25`, 2 bytes (undecoded) |

The sizes add up to 7 + 16 + 4 + 2 + 3 + 1 + 2 = 35, the record size.

Field codes recur across tables with the same meaning: `0x0d` = text,
`0x0e` = 4-byte flags (5 bytes in table 22), `0x0f` = 3-byte BCD amount,
`0x10` = 2-byte number.

**Table header** (`f`, 18 bytes). Confirmed:

| Offset | Size | Content |
|---|---|---|
| `+0` | 2 | `66 00` tag |
| `+2` | 1 | Table id (same as the id in the descriptor) |
| `+3` | 2 | `01 00` |
| `+5` | 1 | Unknown: `03` for the PLU table, `0A` for tables 1, 2, 5, `01` for the rest |
| `+6` | 3 | `00 00 00` |
| `+9` | 4 | Record size (`u32le`) |
| `+13` | 3 | `01 00 00` |
| `+16` | 2 | Record count (`u16be`) |
| `+18` | | `count * size` bytes of records, no padding between them |

Note the mixed byte order: the record size is little endian, the count is big
endian (`09 C4` = 2,500).

## PLU table (id 4)

The product list: 2,500 records of 35 bytes, starting at `0x6B4`.

| Offset | Size | Field (code) | Meaning |
|---|---|---|---|
| 0 | 7 | `0x22` | PLU code, BCD, padded with `E`. Zero bytes if not assigned |
| 7 | 16 | `0x0d` | Name, CP932, space padded |
| 23 | 4 | `0x0e` | Flags. Byte 1 (offset 24) is `0x40` on 49 records; all other flag bytes are zero. Meaning unknown |
| 27 | 2 | `0x10` | Department number, `u16be` (value 1..4 in use, 0 for unused slots) |
| 29 | 3 | `0x0f` | **Price**, BCD yen (`00 11 00` = 1,100) |
| 32 | 1 | `0x18` | Always `00` |
| 33 | 2 | `0x25` | Undecoded. Byte 34 is always `0x23` on used records, byte 33 varies (`0x26`..`0xAF`). Not a simple checksum of the other fields |

**The PLU number is the record number** (1-based). Confirmed: the PLU code stored
in the record equals the record number for all 64 records that have one.

### Content of this snapshot

| Records | State |
|---|---|
| 1..72 | Products: 65 with names, plus 2 with data but a blank name (22, 23). Gaps with the default name: 25, 26, 27, 49, 70 |
| 73..216 | Default name `PLU0073` ... `PLU0216`, all-zero tail (unused) |
| 217..2500 | Blank name, all zero |

In total 149 slots (the gaps above and 73..216) carry the default name `PLUnnnn`.
216 = 72 x 3: these are the PLUs that the keyboard layout (table 74) can reach
directly; higher numbers can be reached only by typing the code.

Real products: `1` Borshch 1,100; `2` Varenyky 770; `6` Chicken Kyiv 1,650; `32` Lunch A
1,600; `51` Champ Bottle 5,280; `65` Coffee/Te 550; `69` Beer 770; `72` BIOLOGIST
INTRIG 7,750. Departments: 1 drinks, 2 food, 3 sets, 4 alcohol (the 2 blank-named
records 22 and 23 are in department 3 with price 0). Names are cut to 16
characters (`BIOLOGIST RENAIS`, `Varenyky Mushroo`).

Use the full export with `bin/extract_plu_settings.rb` (see "Extracting the data").

### Group names (id 6) and staff (id 7)

### Hourly slots (id 9)

24 x 4 bytes: two `u16le` values, the start and end hour, **stored as BCD** (hour
`10` is `0x10`, so a naive decimal read gives 16). Slot 1 is `00-01`, slot 24 is `23-00`.
These are the 24 rows of the hourly report (009).

### Tax rates (ids 25, 27) - probable

4 x 8 bytes each. Table 25 (fields `0x44` 3 bytes, `0x45` 3 bytes, `0x46` 1 byte, `0x47` 1 byte):

| # | Bytes | Reading |
|---|---|---|
| 1 | `10 00 00 00 00 00 50 03` | 10.00 %, flag `50`, mode `03` |
| 2 | `10 00 00 00 00 00 00 02` | 10.00 %, mode `02` |
| 3 | `08 00 00 00 00 00 50 03` | 8.00 % (reduced), flag `50`, mode `03` |
| 4 | `08 00 00 00 00 00 00 02` | 8.00 %, mode `02` |

The first byte is the rate in BCD. The two rates match the 10 % and 8 % (`※`)

Table 27 has the same shape with all rates zero (a second, unused tax set).

### Settings time stamp (id 29)

`40 00 | 15 11 12 17 30 | 00 00 00 00 00`: after a 2-byte value `40 00` there is a BCD
time stamp 2015-11-12 17:30. It is probably the date the program memory was initialised, not
the export time. Probable.

### Receipt message lines (id 32)

36 lines of 24 characters (the printer width, same as the `------------------------`
separator). They are the logo, header, footer and notice texts of the receipt. In this
snapshot 9 lines are filled: line 12 is a greeting, line 17 is the shop's address,
lines 20-21 are the "fold the printed side inward / keep the receipt" notice, lines 26-29
are notices (`臨時休業` closed, `入荷しました` arrived, `千円札が不足しています` out of 1,000-yen bills,
`セール中` on sale) and line 36 is `注）※は軽減税率適用` (note: ※ means reduced tax rate).
The rest are spaces.

### Keyboard layout (id 74) - probable

103 records of 12 bytes = three cells of 4 bytes, each cell `<number: 3 bytes BCD> <kind: 1 byte>`.
Rows 32..103 hold kind `04` with numbers 1..72 in cell 1, 73..144 in cell 2 and 145..216 in
cell 3: the direct PLU keys on three shift levels (216 PLUs, which explains the PLU range in the PLU
table). Rows 17..20 hold kind `05` with 1..4: the four department keys. The remaining rows (kind `02`)
hold small numbers and are probably function keys. Unverified except for the PLU part.

## Extracting the data

### With the project scripts

```bash
# PLU list (table 4 plus department names from table 5), UTF-8 CSV, read-only
ruby bin/extract_plu_settings.rb -o plu_settings.csv "data/CASIO-2026-02-01/SR500_550_4000/AUTOPGM/FILE092P.092"
ruby bin/extract_plu_settings.rb --all ...      # include the 2,433 unused slots
```

The output has `PLU, Name, Price, Department, Department Name, Flags`. Flags is the raw hex of
the four flag bytes plus the department high byte. `lib/sr500_plu_file.rb` finds a table by
searching for the 5-byte prefix `66 00 <id> 01 00` and validating the record size and the
`01 00 00` marker, so it does not depend on fixed offsets.

### Reading any table

```ruby
data = File.binread(path)
raise 'not a FILE092P file' unless data.start_with?('n:P0092:'.b)

tables = {}
pos = 0xA0                                   # first descriptor block
while pos < data.bytesize
  raise "bad block at #{pos.to_s(16)}" unless data.byteslice(pos, 2) == "i\x00".b
  len   = data.byteslice(pos + 2, 2).unpack1('v')      # u16le
  head  = pos + 4 + (len - 1)                          # table header
  id    = data.getbyte(head + 2)
  size  = data.byteslice(head + 9, 4).unpack1('V')     # u32le
  count = data.byteslice(head + 16, 2).unpack1('n')    # u16be
  start = head + 18
  tables[id] = Array.new(count) { |i| data.byteslice(start + i * size, size) }
  pos = start + size * count
end

text = ->(b) { b.dup.force_encoding('Windows-31J').encode('UTF-8').strip }
bcd  = ->(b) { b.unpack1('H*').to_i }                  # only if all nibbles are digits

tables[4].each_with_index do |r, i|                    # PLU table
  name  = text.(r.byteslice(7, 16))
  price = bcd.(r.byteslice(29, 3))
  dept  = r.getbyte(28)
  unused = (name.empty? || name == format('PLU%04d', i + 1)) && price.zero? && dept.zero?
  puts [i + 1, name, price, dept].join(',') unless unused
end
```

If the loop ends exactly at the file size the structure is valid (it does for this file).
Use the layouts above to decode other tables.

### Checks and pitfalls

- Verify the result: 65 PLUs with names plus 2 blank-named records with data in 1..72, and for
  every PLU sold in the journal the price equals a price in `items.csv` (49 of 49 matched).
- The PLU number is the record number, not the code field; they agree for all records that have a
  code.
- Names are cut at 16 characters and trailing spaces must be stripped.
- Default names `PLUnnnn` (with a zero tail) are unused slots, not products.
- This is a Jan 2025 snapshot. The current catalog (70 names at 2026-10-03) and unit prices
  (amount divided by quantity) are in the daily PLU sales report 004: use
  `bin/extract_z_reports.rb` and `z_plu_sales.csv`.
- Do not write to the file; the register may re-import it.
